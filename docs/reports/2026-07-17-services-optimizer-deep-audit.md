# Углублённый аудит оптимизатора сервисов

**Дата:** 2026-07-17
**Ревизия:** ветка `optimization`, `f576517` + незакоммиченные фиксы предыдущей итерации (schemas.py, facade.py, provision_adapter.py, optimizer.py)
**Рамка:** методология («пустой участок → доступная BFA (сервисная доля 0.3) → население из остатка BFA → спрос → TPE-подбор юнитов → конкурентный provision») считается корректной и не пересматривается. Все находки ниже — дефекты *реализации*, которые заставляют код отклоняться от этой методологии, либо дефекты достоверности отчётности.

## 1. Сводка

Границы участка (site area / BFA) в опубликованных решениях соблюдены — подтверждено независимым пересчётом. Но углублённый разбор кода выявил кластер P0-дефектов, из-за которых **objective оценивает не то решение, которое потом отчитывается**, и **допускает сервисы при доказанном отсутствии спроса**. Ключевое эмпирическое подтверждение: в зоне доступности школы (15 мин) от блока 78 существует профицит 2082 места, тем не менее оптимизатор разместил школу на 250 мест — это прямое нарушение принципа методологии «ёмкость в пределах спроса», вызванное правилом надбавки в `CapacityChecker`.

## 2. Дефекты P0 — искажают результат оптимизации

### P0-A. Objective не пересчитывает provision для «неизменившихся» сервисов с учётом населения текущего решения

**Доказательство.** `Facade.get_provisions` (`facade.py:399-431`): для сервисов, не попавших в `changed_services`, provision берётся из `_last_provisions` (значение от *другого* x) или из `_start_provisions` (вообще без нового населения). Принудительный пересчёт при появлении спроса выполняется только если стартовый provision равен ровно 1.0 (`facade.py:410-416`). Если стартовый provision, например, 0.7 — спрос нового населения текущего x для такого сервиса не попадает в objective никогда, пока не меняются его юниты.

**Эффект.** Решение «строить меньше сервисов, больше жилья» не штрафуется: новые жители создают спрос, но provision пропущенных сервисов остаётся стартовым. `best_val` систематически завышен; сравнение trial'ов некорректно. Это тот же класс дефекта, что закрытый ранее P0-1, но живущий внутри objective.

**Смежный баг.** В `get_changed_services` условие (`facade.py:369-377`)
`... or var.count > 0 and var.count != var_last.count` из-за приоритета операторов не считает изменением переход `count: N → 0`: сервис, полностью убранный из решения, помечается «неизменившимся» и получает стартовый provision без учёта нового спроса.

### P0-B. Итоговый score provision теряет добавочный спрос блоков без локального юнита (P0-2 закрыт наполовину)

**Доказательство.** `ProvisionAdapter.calculate_provision`: добавочный спрос всех residential-блоков корректно включён во **вход** LP (`provision_adapter.py:196-213`), но **итоговый scoring-DataFrame** собирается иначе: `new_provision_df["demand"] = start["demand"]`, и добавка `max_population` прибавляется только по `delta_df.index` — блокам, где размещены юниты данного сервиса (`provision_adapter.py:230-231`). Спрос блоков без локального юнита отсутствует в знаменателе `provision_strong_total = Σ demand_within / Σ demand` (`core.py:151-152`), при том что их удовлетворённый спрос попадает в числитель через LP.

**Эффект.** Provision завышается (в вырожденных случаях может превысить 1.0). Фикс P0-2 исправил вход LP, но не скоринг.

### P0-C. Преобразование x → решение нестабильно: чередующаяся «дельта»-семантика конвертера

**Доказательство.** Три связанных тумблера состояния:
- `VariableAdapter.update_x_prev` (`variable_adapter.py:177-184`): `_X_prev` попеременно `None` / копия предыдущего решения — вызывается из `update_cap` после каждой оценки (`facade.py:431`);
- `Constraints.update_solution` (`constraints.py:87-99`): `_prev_solution` — тот же попеременный паттерн;
- в «дельта»-режиме конвертер стартует с копии предыдущего решения и обнуляет остаток BFA для residential (`area_solution.py:193-201`), а `suggest_solution` задаёт нижние границы `lb = prev_val` и обнуляет BFA-лимит (`constraints.py:381-390`).

**Эффект.** Один и тот же вектор `x` конвертируется в разные наборы юнитов в зависимости от чётности trial'а. В логах это видно напрямую: значения objective идут парами (trial 0 = trial 1, trial 2 = trial 3) при совершенно разных векторах параметров. Главное следствие — **отчётное решение не совпадает с оценённым**: `get_best_x()` возвращает сырые параметры лучшего trial (`optimizer.py:391-400`), а `solution_to_services_df`/`get_solution_area_df` переконвертируют их уже в другом состоянии конвертера. Скорректированное решение `correct_x` сохраняется в `user_attrs` trial'а (`optimizer.py:367-368`), но для отчёта не используется.

### P0-D. Надбавка «+1 юнит» в CapacityChecker разрешает сервис при нулевом и даже отрицательном дефиците

**Доказательство.** `CapacityChecker.add_service_type` (`capacity_checker.py:45-66`): к catchment-спросу всегда прибавляется ёмкость одного юнита; при `block_demand = 0` условие `any(units.capacity >= 0)` истинно, и бюджет становится равным ёмкости наименьшего юнита. Эмпирика (данные аудита, блок 78): школа, радиус 15 мин — население 1 065 940, нормативный спрос 127 913, существующая ёмкость 129 995, **профицит 2082**; оптимизатор разместил школу на 250 мест. Детсад: наивный дефицит 317 мест — размещено 720.

**Эффект.** Один юнит любого сервиса допустим всегда, независимо от спроса; в паре с P0-E (ниже) появляется прямой стимул строить ненужные объекты. Это отклонение реализации от методологии («сервисы в пределах спроса зоны доступности»), доказанное данными.

### P0-E. При нулевом спросе provision = 0, а любой юнит превращает его в 1.0

**Доказательство.** `provision_adapter.py:217-220, 242-245`: `demand.sum()==0 → return 1.0 if capacity>0 else 0`.

**Эффект.** Сервис, который никому не нужен, даёт 0 в objective; размещение одного юнита флипает вклад в weight×1.0 — вознаграждение за бесполезное строительство. Корректная семантика при нулевом спросе — provision 1.0 (нечего обеспечивать) независимо от ёмкости.

### P0-F. x не управляет embedded-юнитами: жадная добивка до лимитов

**Доказательство.** `AreaSolution._inject_area_to_X` (`area_solution.py:149-158`): для юнита с `site_area = 0` величина добавки `addition = min(cap_limit, bfa_limit)` не зависит от значения переменной x (площадочный бюджет `_blocks_sa` расходуется только юнитами с `site_area > 0`). Embedded-юниты добираются жадно до лимитов BFA/ёмкости при любом x.

**Эффект.** Значительная часть решения (96 из 294 юнитов конфигурации — embedded) не является функцией переменных оптимизации: TPE видит плоский ландшафт (в логах разные x дают идентичный objective), а «поиск» вырождается в жадную укладку в фиксированном порядке сервисов. Поэтому лучшим почти всегда остаётся trial 0.

**Смежный баг.** В условии сопоставления юнита пропущен `abs()`: `(x.build_floor_area - u.build_floor_area) < 1e-6` (`area_solution.py:146`) — совпадением считается любой юнит с BFA *меньше* эталонного при равных capacity/site_area.

## 3. Дефекты P1 — достоверность метрик и инфраструктура поиска

### P1-A. Отчётные метрики вводят в заблуждение
- `reported_bfa`/`residual_bfa`: `get_solution_area_df` суммирует **бюджет** (`facade.py:747`), а не факт → `residual_bfa ≡ 0`.
- `func_evals` — число пересчётов provision по сервисам (`objective.py`: `_current_func_evals += len(changed_services)`), а не число оценённых решений.
- `success_rate` — доля непруненных trial'ов, не качество.
- `best_val` не нормирован: сумма весов ≈ 0.93.

### P1-B. Три несовпадающие формулы добавочного спроса
`facade.get_delta_demand`: `floor(floor(bfa·2.333/25)/1000·d)`; `provision_adapter.calculate_provision`: `floor(bfa·2.333·d/25000)` (`provision_adapter.py:207-208`); `CapacityChecker` использует стартовый `demand_left`. Feasibility и скоринг расходятся на ±1 на блок/сервис; правило дискретизации P1-3 применено только в фасаде.

### P1-C. Незасеянный и частично сломанный поисковый контур
- `TPESampler` без seed (`optimizer.py:201-207`); параметр `seed` в harness объявлен и не используется (`run_5blocks_audit.py:89, 188`) → воспроизводимости нет (наблюдалось: 2 прогона — разные решения тех же блоков).
- `WeightChooser` сломан: `services_list.sort(lambda x: ...)` — TypeError в Python 3 (`variable_choosing.py:152`); дефолтная ветка `WeightChooser()` без обязательных аргументов (`optimizer.py:212`) упадёт при `vars_chooser=None`.
- `GradientChooser` индексирует сохранённые `params` trial'а как вектор x-пространства, тогда как в `user_attrs` записан `correct_x` — вектор счётчиков юнит-пространства другой длины и семантики (`variable_choosing.py:224` против `optimizer.py:367-368`) → «градиенты» вычисляются по чужому вектору.

### P1-D. Вход harness противоречит заявленной методологии
`run_5blocks_audit.py:60-68` подставляет `footprint_area` существующих зданий как `site_area`. Для блока 78 фактическая площадь территории 2 842 930 м², а бюджеты посчитаны от футпринта ~8 097 м². Методология оперирует «площадью территории» пустого участка; текущий вход — площадь пятна старой застройки. Требуется решение о корректном входе (площадь застраиваемой части территории), это вопрос подготовки данных, не кода оптимизатора.

### P1-E. Мелкие риски
- `old_provision_df.loc[block_id, "demand"] += pop` бросит KeyError, если residential-блок вне provision-контекста (`provision_adapter.py:213`).
- `_check_stop` не останавливает исследование после «suggested»-trial'а даже при исчерпании `max_evals` (`optimizer.py:404-420`) — переисчерпание лимита на один trial.

## 4. Что подтверждено как корректное

- Соблюдение лимитов SA/BFA в итоговых решениях (независимый пересчёт по 5 блокам).
- Арифметика «остаток BFA → население»: `floor(residual·(1/0.3−1)/25)` — сходится во всех блоках; суммарная застройка не превышает FSI×A.
- Инлайн `parking_area` в ресурсы юнитов (P0-3) — подтверждён в runtime (embedded-школа 2200+200=2400).
- Обнуление населения и ёмкостей целевого блока в сценарии «пустой участок» (`provision_adapter.py:46, 78`).
- Конкурентный LP `competitive_provision` — постановка и ограничения корректны (спрос/ёмкость как ограничения потока, максимизация взвешенного потока).
- Фиксы прошлой итерации P0-1 (demand текущего x в `check_constraints`) и P1-3 (порядок округления в фасаде) — корректны в своей зоне действия.

## 6. Приоритет реализации

P0-A/B (честный objective) → P0-C (детерминизм конвертера и отчёта) → P0-D/E (спросовые границы) → P0-F (управляемость embedded) → P1-A (метрики) → P1-B (единая формула спроса) → P1-C (seed, chooser'ы) → P1-D (вход harness — отдельное решение по данным).
